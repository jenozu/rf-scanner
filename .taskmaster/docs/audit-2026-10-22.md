# RF Scanner (Marindustrial) — Audit Report & Completion Plan

Audited: `jenozu/rf-scanner`, `main` @ `4073d33` (2026-10-22). Nothing in the repo or on production was changed.

## Bottom line

The app *looks* finished and builds cleanly, but the warehouse transactions are not saved where other people or devices can see them. Receiving, picking, counting and bin changes are written only to the browser on the device that did the work. PO/SO imports on the Setup page go to the server only, and Receive/Pick never read them. The backend also lets any logged-in user become admin or delete the admin. The shipping module cannot work in the current Docker setup. These are fixable without rewriting, but they come before anything else.

**What I ran:** `npm ci`, `tsc --noEmit` (passes), `vite build` (passes). The backend was started locally on a temporary data folder and I made 12 API calls against it. The PO/SO parsers were run with test rows. I loaded the production home page once (read-only). **Not reviewed in depth:** `inventory-page.tsx` (3,136 lines), `scan-page.tsx` internals, the Purolator Python code beyond how Node calls it, and the redesign screenshots. There are **zero automated tests** in the repo.

## 1. Current state

A React + TypeScript single-page app (Vite, Tailwind, Quagga camera scanner) with a small Node/Express API that stores JSON files on disk, plus a Python folder (`puro/`) for Purolator shipping. Deployed on a VPS with Docker (nginx container serves the app and proxies `/api` to the Node container; Traefik routes `rf.andel-vps.space`). The Marindustrial redesign is merged to `main`.

**Production may not have the redesign yet.** The live page's title is still "RF Inventory Counter" with the old blue theme colour, while `main` says "RF / WMS — Warehouse Operations" with navy `#0a1f2e`. One page fetch, so treat as indicative; worth confirming on the VPS.

## 2. Working (verified)

- Build and type-check pass; code-splitting works.
- Login with bcrypt-hashed passwords and 24-hour JWT tokens.
- Master inventory import (CSV/XLSX) saves to the server and builds bins.
- Bin-range locks for counting sessions are server-side, so two people can't count the same range.
- PO and SO parsers keep SAP line numbers as separate lines, even when the same ItemCode appears twice. Your sample `PO/*.csv` files parse correctly (`poNumber, vendor, CardCode, LineNumber, ItemCode, Description, OrderedQty, ReceivedQty, BinCode`).
- Demo mode is properly walled off (see Architecture).

## 3. Partially complete

- **Receiving:** a good screen (numpad, lots/serials, bin pick) but it only saves to this device (see Risks 1–2).
- **Picking:** same pattern. Sorted by bin, quantity checked against remaining; no scan confirmation.
- **Cycle counting:** big feature set (sessions, sequential/full counts, bin ranges), saved in the browser. Only bin locks reach the server. Not reviewed line by line.
- **Dashboard:** real numbers, but computed from *this browser's* storage, so it's a per-device dashboard.
- **SAP import:** works for the happy path; gaps listed in section 4.
- **Exports:** inventory CSV works. Receiving and count logs export from the server, which never has them (section 4).
- **Docs:** ~55 markdown files, many stale or contradicting each other.

## 5. Production risks

**Data loss / wrong transactions**
1. Transactions live in one browser. Clearing site data, a different handheld, or a replaced device loses or splits the real stock picture.
2. Two handhelds working the same warehouse see different quantities. Nothing reconciles them.
3. Server saves overwrite the *whole file*, non-atomically, with no versioning. Two simultaneous saves, last one wins. Failed saves are silent (fire-and-forget).
4. Repeated-ItemCode orders get wrong quantities (4b).

**Security (all verified against a local copy of the server)**
5. **Any logged-in user can do anything.** An operator token successfully promoted itself to admin and deleted the real admin account. "Admin only" is enforced in the browser only.
6. **`POST /api/users/init-admin` is unauthenticated** and creates `admin / admin123` whenever the user list is empty.
7. **JWT secret falls back to a public default** in source. With it I forged an admin token and read data. Whether production sets `JWT_SECRET` in `server/.env` is unknown to me. Please check on the VPS.
8. No login rate limiting (51 bad logins in a row, all just 401). Passwords only need 3 characters. CORS is open.
9. **Company data is in a public GitHub repo:** `master_inventory.xlsx` (twice, 223 KB), 8 real PO files with vendor names, `data/users.json` (the admin's bcrypt hash from Nov 2025), `puro/customer_addresses.db`, and a 3 MB `rf-scanner-deploy.tar.gz`. The tarball's `.env` holds only `VITE_*` names (no credentials). Removing them from history is a separate decision.
10. If the VPS `./data` folder holds the same files, nginx serves it at `/data/...` with no login. Needs a check on the VPS. I did not probe production for this.
11. `npm audit` reports 6 issues on the server (1 critical, 4 high) and more on the frontend.

**Deployment**
12. ~8 old deploy scripts (`deploy-*.ps1`, `deploy-rf.sh`, pm2 config, `/var/www/rf-scanner` paths) describe the old non-Docker setup. Docker + Traefik is the real one. Easy to run the wrong thing.
13. CI runs only on the redesign branch, never on `main` or pull requests. `PREVIEW.md` mentions "preview isolation checks" in the build; `package.json` has none.
14. `puro/test_production_auto.py` is named a test but creates a real Purolator label.

## 6. Architecture (plain language)

```
Handheld/PC browser ──► rf.andel-vps.space (Traefik)
                           └─► nginx container: serves the React app, forwards /api/* ─┐
                                                                                        ▼
                                          Node/Express container ── JSON files in a Docker volume
                                                                    └─ (intended) runs Python in puro/ → Purolator
Browser storage (localStorage) ← where most warehouse work is actually saved today
```

- **Frontend:** React pages; one `api.ts` client adds the login token. Shipping bypasses it.
- **Backend:** one `server/index.js` (~890 lines): users, a generic "save this JSON blob under this key" endpoint, bin locks, shipping routes.
- **Storage:** server = whole-file JSON. Browser = localStorage (what most screens use).
- **SAP:** no live connection. Staff import CSV/XLSX files. Optional Python exporters for a machine with SQL access (`export_po_from_sap.py`, `inventory_export_for_rf.py`); not part of the Docker deploy.
- **Purolator:** Python scripts (`puro/`), meant to be called by Node. See 4c.
- **Demo vs real:** demo mode switches on when `VITE_DEMO_MODE=true` **or** the hostname ends in `.vercel.app`. In demo mode every API call goes to a fake in-browser backend and shipping is simulated. The Docker build sets neither, so production is real mode. Risk: if the real app were ever hosted on a `.vercel.app` address it would silently turn into demo. The demo uses the same storage key names as the real app, but only on its own web address.

## 7. Recommended MVP

**Must have**
- One shared source of truth: POs, SOs, bins, inventory and every transaction saved on the server and visible to every device.
- Real roles enforced by the server; no default or guessable admin; required `JWT_SECRET`.
- PO and SO import that keeps SAP DocNum + line number as the identity of each line, handles Excel dates and numbers, keeps Warehouse and Bin separate, and can update an order on re-import.
- Receiving and picking that act on the specific line, never over-receive, and write a transaction record.
- Barcode scan confirmation in picking (and receiving where items have barcodes).
- Exports shaped for SAP (receipts, picks/deliveries, count results) that include DocNum and line number.
- Backups of server data and a sane deploy procedure.
- Automated tests for parsers and quantity math; CI on `main`.

**Should have**
- Cycle-count posting file for SAP, with variance review.
- Working shipping: Python (or a Node port) available to the API, authenticated calls, persistent address book.
- Server-wide dashboard; activity log with real user attribution.
- Offline tolerance: queue failed saves and show clear sync status on handhelds.
- Cleanup of stale docs and deploy scripts.

**Later**
- Direct SAP integration (Service Layer / DI-API) once access exists.
- Lot/serial depth, putaway suggestions, wave picking improvements, label printing.
- Database (SQLite/Postgres) instead of JSON files, if volume or concurrency demands it.

## 8. Completion plan

**Phase 1 — Safety & baseline** *(small, no workflow changes)*
- *Objective:* close the security holes and add a test/CI net before more real data flows through.
- *Tasks:* server-side admin checks on user routes; remove public `init-admin` (replace with a one-time setup via env var / script); fail to start without `JWT_SECRET`; login rate limit; stricter passwords; correct key allow-list; stop committing data (`git rm --cached`, `.gitignore`); Vitest + CI on `main`/PRs; `npm audit fix` where safe.
- *Files:* `server/index.js`, `.gitignore`, `package.json`, `.github/workflows/`.
- *Tests:* API tests for permission boundaries (operator can't create/promote/delete users); build + typecheck in CI.
- *Done when:* the 12 checks I ran by hand now fail correctly and run automatically.

**Phase 2 — One source of truth**
- *Objective:* every device sees the same orders, stock, and history.
- *Tasks:* proper server endpoints per record (orders, bins, transactions) with per-record updates and atomic writes; one data layer in the frontend replacing scattered `localStorage` use; visible save/sync errors; one-time migration of existing browser data (with your OK); nightly backup.
- *Files:* `server/`, `src/services/`, `src/hooks/`, receive/pick/inventory/home/export pages.
- *Tests:* two-client concurrency test; failed-save behaviour; migration test.
- *Done when:* receiving on one device appears on another within a refresh, and clearing a browser loses nothing.

**Phase 3 — SAP import fidelity**
- *Objective:* imports are exact and repeatable.
- *Tasks:* inspect your real SAP XLSX exports first; stable line identity (DocNum + LineNum); Warehouse and BinCode as separate fields; Excel dates; number parsing; validation report (rows skipped and why); re-import updates open quantities without losing received history.
- *Files:* `csv-utils.ts` (split into import module), `types/index.ts`, setup/receive pages.
- *Tests:* fixtures for each format incl. duplicate ItemCodes, closed lines, date cells.
- *Done when:* the same SAP file imported twice gives identical results and a changed file updates correctly.

**Phase 4 — Receiving & picking correctness**
- *Objective:* quantities are right per line.
- *Tasks:* act on line identity; cap over-receipt (supervisor override optional); scan confirmation for picks; short-pick handling; stock decrement/increment per bin with checks.
- *Tests:* duplicate-ItemCode scenarios; partial receipts; over-pick refusal.
- *Done when:* a PO and an SO each containing two lines of the same item process correctly end to end.

**Phase 5 — SAP-ready exports**
- *Objective:* clean results can go back into SAP B1.
- *Tasks:* agree target SAP import templates with you (GRPO, Delivery, Inventory Counting); export with DocNum/LineNum, qty, bin, user, timestamp; export history/"already exported" flag.
- *Done when:* a sample export imports into your SAP test company without edits.

**Phase 6 — Shipping**
- *Objective:* Purolator labels from the real deployment.
- *Tasks:* add Python + dependencies to the API image (or port the calls to Node); fix the stdin call; send auth token from the shipping page; put the address book on a volume; confirm credentials come from env vars; sandbox testing before any live label.
- *Done when:* a test-account shipment returns a PIN from the production-style container.

**Phase 7 — Counting, bins, dashboard**
- *Objective:* make counting trustworthy and the dashboard organisation-wide.
- *Tasks:* review `inventory-page.tsx` on the new data layer (and split the 3,136-line file); numeric-aware bin ranges (the lock check compares text); variance approval; server-driven dashboard.

**Phase 8 — Deployment & documentation**
- *Objective:* one documented way to deploy and restore.
- *Tasks:* remove obsolete scripts; one README; deploy checklist with rollback; Vercel kept for demo only.
- *Done when:* a fresh VPS can be rebuilt from the README.

## 9. Immediate next step

**Start with Phase 1.** It's small, it doesn't change how staff work, and every later phase writes more real data through this API. As it stands, any operator account can erase the admin, so building the shared-data layer on top of that first would be backwards. Phase 2 follows directly.
